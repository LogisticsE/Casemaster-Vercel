cms-vercel

A serverless runtime that lets CaseMaster .cms applications deploy to Vercel — no long-running .NET host, no Windows-only binaries, no CaseMaster.Web.exe. Same source files, same Postgres, same URLs.

v0.1.0 — internal preview not yet on npm

What it does

CaseMaster ships a closed-source .NET interpreter for the .cms language. It needs a long-running Windows host, which excludes Vercel and most modern serverless platforms. cms-vercel re-implements just enough of that interpreter — the lexer, parser, BO registry, page renderer, and Postgres pool — in TypeScript, packaged as a single Vercel Function. Push your .cms files to GitHub, and Vercel builds + serves them on every commit.

Why use it

Problemcms-vercel answer
Need a Windows host to run CaseMaster Linux serverless functions, scales to zero
Manual deploys, port-forwarded boxes git push → live URL in ≈30 seconds
BO maintenance pages take effort to scaffold Auto-generated /maintenance/<bo> CRUD UI
Want preview deployments per branch Built into Vercel's Git integration; works out of the box

Quickstart

From any laptop with Node 20+ and a Vercel account:

git clone https://github.com/LadFoxTom/Casemaster-Vercel my-app
cd my-app
rm -rf .git && git init                   # detach from upstream
npm install
cp .env.example .env.local                # paste your DATABASE_URL

# (optional) import your existing CaseMaster source
node packages/runtime/bin/import.mjs --from /path/to/casemaster-runtime

npm run dev                               # http://localhost:3000

git remote add origin git@github.com:<you>/<your-repo>.git
git push -u origin main                   # then connect on vercel.com

Full walk-through with troubleshooting tips: HOWTOLAUNCH.md.

Live demos on this deployment

Hello world page

Full HTML page through <@page/container> + resolveTemplate + a CSS asset from /static/.

DB connectivity

Hits Postgres' information_schema.tables through sql.fetch + an iterate loop.

Runtime stats

JSON probe: registry warmth, function/resource/BO counts, cold-vs-warm-start signal.

The auto-CRUD demo (/maintenance/<bo>) needs at least one <@bo> declaration in app/bo/. This deployment ships zero so the demo stays free of project data — drop a single BO file in and the maintenance UI appears with no other code change.

What's supported

  • Page routing (/page/<script>/f/<fn>) and auto BO maintenance (/maintenance/<bo>).
  • The full read + write BO surface (iterator.ofEntity, bo.attr/persist/delete), plus raw sql.execute / sql.fetch.
  • resolveTemplate({{…}}), script.call, page.get / page.render, the standard library (dates, strings, JSON, PB).
  • Outbound HTTP (httpRequest.create), Postgres-backed sessions + cookies, static assets, scheduled jobs via vercel.json crons.
  • A build-time validator (cms-vercel-build) that flags unsupported builtins with file:line:col before deploy.

Full reference: API.md · Migration guide: MIGRATION.md · What doesn't work (yet): UNSUPPORTED.md.

How it's distributed

Today: git clone from the GitHub repo. The runtime lives inside packages/runtime/ and ships with each deploy. It will move to npm (npm install cms-vercel + npm create cms-vercel) once the licensing question is sorted with the CaseMaster vendor.

Diagnostics

  • /api?diag=1 — registry health, app dir, env-var presence.
  • /api?stats=1 — function counts + warm-instance status.
